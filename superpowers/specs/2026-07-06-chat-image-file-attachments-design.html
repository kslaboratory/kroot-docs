main-site aicoding 채팅 — 이미지·파일 첨부 처리 (node-executor) ​

  • 작성일: 2026-07-06
  • 대상 레포: kroot-adk (node-executor/executor.mjs)
  • 참조 구현: /Users/jikime/Dev/Private/cli-relay/client/node-executor (이미지 슬라이스)

1. 목표 ​

main-site aicoding 채팅에서 사용자가 이미지와 파일을 업로드하면, 릴레이를 거쳐 로컬 에이전트(claude-agent-sdk)가 그것을 처리하도록 한다.

  • 이미지 — 모델이 직접 보도록 user 메시지에 image content block 으로 인라인.
  • 파일(코드/텍스트/PDF/문서 등) — 로컬 workspace(cwd) 하위 전용 폴더에 저장하고, 저장 경로를 프롬프트에 알려 에이전트가 Read/Grep/편집 도구로 다루게 한다.

2. 아키텍처 — main-site 경로는 executor.mjs 한 곳만 바꾼다 ​

브라우저 → 릴레이(kroot-server /ws/browser) → 데몬(kroot chat start = internal/chatagent) → 로컬 executor(node-executor/executor.mjs).

핵심 사실(코드 확인):

  • 데몬 chatagent.Run 은 릴레이 프레임을 verbatim 으로 executor stdin 에 전달한다 (c.Read → executor.WriteRaw(data); WriteRaw 는 프레임에 \n 만 덧붙임).
  • executor.mjs 는 stdin 을 줄 단위 JSON 으로 읽는다(createInterface).
  • 따라서 브라우저가 보낸 JSON(req)이 그대로 executor 에 도착한다.

결론:

  • 필수 변경은 executor.mjs 한 파일뿐이다.
  • 변경하지 않는 것: Go executor.ChatRequest(CLI kroot chat run 전용, main-site 경로와 무관), 릴레이 서버(verbatim 중계). Go CLI parity 는 이번 범위에서 제외(YAGNI).

3. 와이어 계약 (브라우저 → executor stdin JSON) ​

기존 chat 요청에 images(이미 cli-relay 에 정의됨)와 files(신규)를 추가한다. 둘 다 선택.

jsonc
{
  "type": "chat",
  "prompt": "이 목업대로 고쳐줘",
  "cwd": "/Users/me/proj",
  "sessionId": "…",
  "images": [
    { "data": "<base64, data: 접두부 없이 순수 base64>", "mimeType": "image/png" }
  ],
  "files": [
    { "name": "spec.pdf", "data": "<base64>", "mimeType": "application/pdf" }
  ]
}
  • images[].mimeType 지원: image/jpeg|png|gif|webp (모델 vision 지원 포맷).
  • files[].name 은 원본 파일명, files[].data 는 순수 base64, mimeType 은 선택(로깅/향후용).
  • data 는 data URI 접두부(data:...;base64,) 없이 순수 base64 여야 한다. 접두부 제거 책임은 main-site(브라우저)에 있다(§8 계약).

4. 이미지 처리 (cli-relay 슬라이스 포팅) ​

userMessage(text, images) 로 확장 — images 를 앞에, text 를 뒤에 두어 content 배열 구성:

js
content.push({ type: 'image', source: { type: 'base64', media_type: img.mimeType, data: img.data } })
// … 모든 이미지 후
content.push({ type: 'text', text })

validateImages(images):

  • undefined → true(이미지 없음).
  • 배열이고 length ≤ MAX_IMAGE_COUNT(20).
  • 각 항목: data 는 비어있지 않은 string, mimeType 은 지원 목록에 포함.

이미지는 디스크에 저장하지 않는다(인라인 전용).

5. 파일 처리 (신규) ​

5.1 저장 위치·수명 ​

  • <cwd>/.kroot/uploads/<turnId>/ 에 저장. turnId = 타임스탬프 + 짧은 랜덤 (Date.now() + randomUUID().slice(0,8); executor 는 실제 laptop Node 프로세스라 사용 가능).
  • 유지(세션 종료 후 삭제하지 않음) — 사용자가 다시 참조 가능.
  • cwd 하위라 에이전트 파일 도구(Read/편집)가 바로 접근 가능.

5.2 파일명 안전 처리 ​

  • path.basename(name) 으로 디렉터리 성분 제거 → 경로 traversal 차단.
  • .., 경로 구분자, 제어문자, 널바이트 제거/치환. 빈 이름이 되면 file 로 대체.
  • 같은 turn 폴더 내 충돌 시 name (2).ext, name (3).ext … 로 rename.

5.3 프롬프트 증강 ​

파일 저장 후, 사용자 text 뒤에 저장된 절대경로 목록을 덧붙여 모델에 알린다:

<원본 prompt>

[첨부된 파일 — 로컬 경로]
- /Users/me/proj/.kroot/uploads/1720…-a1b2c3d4/spec.pdf
- /Users/me/proj/.kroot/uploads/1720…-a1b2c3d4/data.csv

이 증강된 text 가 userMessage(augmentedText, req.images) 로 들어간다. 파일이 없으면 원본 text 그대로.

5.4 헬퍼 경계 ​

  • validateFiles(files) — undefined→true; 배열이고 length ≤ MAX_FILE_COUNT(20); 각 항목 name 비어있지 않은 string, data 비어있지 않은 string, mimeType 있으면 string. fail-closed.
  • materializeFiles(cwd, files) → { paths: string[], note: string } — 폴더 생성·sanitize·충돌 rename·base64 디코드 write 후, 절대경로 배열과 §5.3 note 를 반환. I/O 실패는 명확한 에러로 throw.

6. 검증 & 사이즈 예산 (하드 실링 실재) ​

릴레이(kroot-server maxMessageBytes = 16 MiB, browser·agent 양 leg SetReadLimit)와 데몬(SetReadLimit(16<<20)) 둘 다 프레임 16 MiB 한도다. 초과하면 ws 가 즉사 → 재접속 폭풍 + UI 깜빡임. 따라서:

  • 상수: MAX_IMAGE_COUNT=20, MAX_FILE_COUNT=20, SUPPORTED_IMAGE_MIME_TYPES = jpeg/png/gif/webp.
  • 총합 예산: images[].data + files[].data 의 base64 길이 합이 MAX_TOTAL_ATTACHMENT_CHARS (≈ 12 MiB, 16 MiB 프레임 실링 아래 — base64 팽창 감안)를 넘으면 거절.
  • executor.mjs 는 backstop 이다(마지막 동기 체크). 실제 UX 방어는 main-site 가 업로드 전 총량을 거절하는 것(§8 계약).
  • 모든 검증은 fail-closed: 형태/한도 위반 시 조용히 통과시키지 말고 명확한 {type:'error'} 로 응답하고 그 턴을 중단.

7. executor.mjs 통합 지점 ​

handleChat(stdin req 처리) 진입부에서:

  1. validateImages(req.images) + validateFiles(req.files) + 총합 예산 검사 → 실패 시 out({type:'error', …}) 후 return. (buildOptions 안 throw 가 아니라 여기서 bool 체크 — live-session fast-path 는 buildOptions 를 안 거치므로.)
  2. materializeFiles(resolveCwd(req), req.files) → { paths, note }. 파일 있으면 text 에 note append.
  3. userMessage(augmentedText, req.images) 를 두 경로 모두에 적용:
    • live 세션 재사용 fast-path (active.input.push(...))
    • 신규 query (input.push(...))

8. 범위 밖 / 다른 레포 계약 ​

  • Go executor.ChatRequest / CLI kroot chat run: 변경 안 함(YAGNI). 필요 시 후속.
  • 릴레이(kroot-server): 변경 안 함(verbatim). 16 MiB 프레임 한도는 유지.
  • main-site(브라우저, 별도 레포): 반드시 지켜야 할 계약 — (a) images/files 를 §3 shape 로 전송, (b) data 는 순수 base64(데이터 URI 접두부 제거), (c) 업로드 전 총량 ≈12 MiB 이하 로 자체 거절(프레임 실링 초과 방지).

9. 테스트 (의존성 0, node --test) ​

  • executor.mjs 를 임포트 가능하게: cli-relay 의 export + isMainModule(realpath 정규화) 가드 포팅 — 임포트 시 main() 이 stdin 을 물고 멈추지 않도록.
  • 유닛테스트:
    • validateImages / validateFiles 경계값(개수·형태·mimeType·총합 예산).
    • userMessage(text, images) content 배열 shape(이미지 앞, text 뒤).
    • 파일 sanitize(경로 traversal ../ 거부), 충돌 rename, 프롬프트 note 형식.
  • package.json 에 "scripts": { "test": "node --test" } 추가.

10. 리스크 ​

  • 총합 예산 vs 프레임 실링: executor.mjs 예산(≈12 MiB)이 backstop 이지만, main-site 가 자체 거절을 안 하면 16 MiB 초과 프레임이 릴레이/데몬 ws 를 끊는다. main-site 계약(§8) 준수가 관건.
  • 대용량 파일: 매우 큰 파일은 base64 로 프레임 실링을 빠르게 소진 → 현실적으로 채팅 첨부는 소형(수 MB)만. 대용량은 별도 업로드(S3) 경로가 맞고, 이번 범위 밖.
  • cwd 신뢰: resolveCwd(req) 가 반환하는 디렉터리에 쓰기 권한이 있어야 한다(실패 시 에러).
