KRoot-ADK 설치 및 스택 연동 가이드 ​

이 문서는 kroot-adk를 설치하고, 필요할 때 kroot-server, kroot-proto, MCP 구성까지 함께 연결하는 방법을 정리합니다. 처음 사용한다면 먼저 CLI만 설치해도 충분하고, 서버와 MCP는 팀에서 로컬 전체 스택을 확인해야 할 때만 차근차근 준비하면 됩니다.

세 저장소를 한 세트로 설치하고 실제 프로젝트에서 사용하는 전체 흐름은 KRoot 통합 설치와 사용 가이드를 기준으로 보면 됩니다.

전체 구성 한눈에 보기 ​

kroot-adk는 개발자 PC에서 실행되는 CLI입니다. 데이터베이스에는 직접 접근하지 않고, kroot-server에 gRPC로 요청을 보냅니다.

text
개발자 PC
  kroot CLI
    |
    | gRPC + JWT
    v
중앙 또는 로컬 kroot-server
    |
    +-- PostgreSQL
    +-- MinIO 또는 S3
    +-- kroot-mcp-gateway

공유 계약
  kroot-proto
저장소역할
kroot-adk개발자 CLI, Claude Code 템플릿, hooks, 로컬 프로젝트 초기화
kroot-servergRPC/REST API 서버, PostgreSQL/S3 접근, MCP Gateway
kroot-protogRPC API 계약의 단일 출처, Go 생성 코드와 OpenAPI 산출물
kroot-ui-refctoring웹 UI와 Prisma schema/migration 소유
@kroot/kroot-mcp-serverUI 저장소 안의 WS Job -> 로컬 CLI 브리지 스캐폴드. 현재 운영 MCP Gateway와는 별도입니다.

로컬에서 전체 스택을 개발할 때는 같은 상위 폴더에 형제 저장소로 둡니다.

text
kaonsoftlab/
  kroot-adk/
  kroot-server/
  kroot-proto/
  kroot-ui-refctoring/

1. KRoot-ADK CLI 설치 ​

macOS (전체 자동 설치, 권장) ​

Node.js·Claude Code 등 필요한 도구가 없다면, 한 줄로 전부 설치합니다. Homebrew(없으면 자동)로 Node.js·Python(최신 3.x)·Git과 Claude Code를 설치하고 kroot까지 설치합니다.

bash
curl -fsSL https://kslaboratory.github.io/kroot-docs/install-mac.sh | bash

옵션: --skip-python, --skip-deps(kroot만), --version X.Y.Z — 예: curl -fsSL .../install-mac.sh | bash -s -- --skip-python

macOS / Linux (kroot만) ​

이미 도구가 준비돼 있거나 kroot 바이너리만 필요하면 이 스크립트를 씁니다. macOS·Linux의 amd64, arm64를 지원합니다.

bash
curl -fsSL https://kslaboratory.github.io/kroot-docs/install.sh | bash

Windows (PowerShell) ​

Windows는 PowerShell 한 줄로 설치합니다. Git Bash가 없어도 되며, 기본적으로 winget으로 Node.js · Python(최신 3.x) · Claude Code(+Git for Windows) 까지 함께 설치합니다.

powershell
irm https://kslaboratory.github.io/kroot-docs/install.ps1 | iex

kroot만 설치하려면(부가 도구 생략):

powershell
& ([scriptblock]::Create((irm https://kslaboratory.github.io/kroot-docs/install.ps1))) -SkipDeps

플래그: -SkipDeps(부가 도구 전체 생략) · -SkipPython · -SkipGitBash · -Version X.Y.Z · -NoModifyPath.

Git for Windows는 선택입니다 — 없으면 Claude Code가 PowerShell을 셸 도구로 사용합니다. 설치가 끝나면 winget이 넣은 PATH를 현재 세션에 다시 로드하므로 바로 kroot·node·python·claude를 실행할 수 있고, 각 도구의 설치 경로도 함께 표시됩니다.

전역 경로인 /usr/local/bin에 설치하려면 다음처럼 실행합니다.

bash
curl -fsSL https://kslaboratory.github.io/kroot-docs/install.sh | bash -s -- --global

특정 버전을 지정해 설치할 수도 있습니다.

bash
curl -fsSL https://kslaboratory.github.io/kroot-docs/install.sh | bash -s -- --version 2.1.0

설치 스크립트는 기본적으로 다음 파일들을 준비합니다.

항목기본 위치
kroot~/.local/bin/kroot
kroot-wt~/.local/bin/kroot-wt

~/.local/bin이 PATH에 없다면 셸 설정에 추가합니다.

bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

설치 확인은 이렇게 합니다.

bash
kroot --version
kroot doctor

Go 개발 환경이 이미 준비되어 있다면 go install도 사용할 수 있습니다.

bash
go install github.com/kslaboratory/kroot-adk/cmd/kroot@latest

소스를 직접 받아 설치하려면 git clone 방식으로 진행합니다. 로컬 개발 빌드는 ../kroot-proto를 참조하므로 두 저장소를 같은 상위 폴더에 두는 것이 중요합니다.

bash
mkdir -p ~/Dev/kaonsoftlab
cd ~/Dev/kaonsoftlab

git clone https://github.com/kslaboratory/kroot-proto.git
git clone https://github.com/kslaboratory/kroot-adk.git

cd kroot-adk
make build

make build와 make install의 차이는 다음과 같습니다.

명령결과주 용도
make builddist/kroot 생성저장소 안에서 빌드가 되는지 확인하거나, 임시로 실행할 때
make installGOBIN에 kroot, kroot-wt 설치터미널 어디서나 kroot 명령을 쓰고 싶을 때

빌드만 확인하려면 make build로 충분합니다. 빌드가 끝나면 실행 파일은 dist/kroot에 만들어집니다. 현재 터미널에서만 바로 쓰려면 다음처럼 PATH에 추가합니다.

bash
export PATH="$PWD/dist:$PATH"
kroot --version

실제 설치까지 하려면 이어서 make install을 실행합니다. 이 타깃은 내부적으로 go install을 사용해 kroot와 kroot-wt를 함께 설치합니다.

bash
make install

# 기본 설치 위치는 $(go env GOPATH)/bin 입니다.
echo 'export PATH="$(go env GOPATH)/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

kroot --version
kroot-wt --version

설치 위치를 직접 정하고 싶다면 GOBIN을 넘깁니다.

bash
make install GOBIN="$HOME/.local/bin"

2. 로컬 kroot-server 준비 ​

팀 서버가 이미 있다면 이 단계는 건너뛰어도 됩니다. 로컬에서 전체 흐름을 확인하려면 kroot-server를 실행해야 합니다.

먼저 kroot-proto가 형제 폴더에 있는지 확인합니다.

bash
cd /path/to/kaonsoftlab/kroot-server
ls ../kroot-proto/proto

로컬 PostgreSQL과 MinIO를 실행합니다.

bash
docker compose up -d postgres minio

기본 포트와 계정은 다음과 같습니다.

항목값
PostgreSQLlocalhost:5432
MinIO S3 APIlocalhost:9000
MinIO 콘솔http://localhost:9001
MinIO 계정minioadmin / minioadmin123

kroot-server는 Prisma migration을 직접 관리하지 않습니다. 데이터베이스가 비어 있다면 kroot-ui-refctoring에서 migration을 적용합니다.

bash
cd ../kroot-ui-refctoring
DATABASE_URL="postgres://kroot:kroot@localhost:5432/kroot_dev?sslmode=disable" \
  npx prisma migrate deploy

다시 kroot-server로 돌아와 환경 파일을 준비합니다.

bash
cd ../kroot-server
cp secrets.env.example secrets.env
chmod 600 secrets.env

로컬 Docker 기본값을 쓴다면 핵심 값은 다음처럼 맞춥니다.

dotenv
KROOT_DB_URL=postgres://kroot:kroot@localhost:5432/kroot_dev?sslmode=disable
KROOT_JWT_SECRET=replace-with-32-or-more-random-bytes
KROOT_S3_ENDPOINT=localhost:9000
KROOT_S3_ACCESS_KEY=minioadmin
KROOT_S3_SECRET_KEY=minioadmin123
KROOT_S3_BUCKET=kroot-files
KROOT_S3_USE_SSL=false

환경 변수를 현재 셸에 올린 뒤 서버를 실행합니다.

bash
set -a
source secrets.env
set +a

go run ./cmd/kroot-server

다른 터미널에서 상태를 확인합니다.

bash
curl http://127.0.0.1:4501/healthz
curl http://127.0.0.1:4501/readyz

/readyz가 {"status":"ready","db":"ok"} 형태로 응답하면 DB 연결까지 정상입니다. gRPC 기본 주소는 grpc://127.0.0.1:4500입니다.

3. ADK에서 서버 로그인 및 프로젝트 연결 ​

kroot-adk는 KROOT_SERVER 또는 --server 값으로 접속할 서버를 정합니다. 로컬 서버를 쓰는 경우 다음처럼 설정합니다.

bash
cd ../kroot-adk
export KROOT_SERVER=grpc://127.0.0.1:4500

사용자 계정은 먼저 웹 UI 또는 DB seed를 통해 생성되어 있어야 합니다. CLI의 auth login은 기존 계정을 검증하고 토큰을 ~/.kroot/credential.json에 저장합니다.

bash
kroot auth login --server "$KROOT_SERVER" --email pm@example.com
kroot auth whoami

로컬 작업 폴더를 원격 kroot 프로젝트와 연결합니다.

bash
# 기존 원격 프로젝트에 연결
cd /path/to/local-project
kroot init --server "$KROOT_SERVER" --project-id <project-id>

이미 초기화된 폴더라면 link만 실행해도 됩니다.

bash
# 기존 프로젝트에 연결
kroot link --server "$KROOT_SERVER" --project <project-id>

# CLI에서 새 프로젝트를 만들고 연결
kroot link --server "$KROOT_SERVER" --create --name "Demo Project"

# 현재 연결 상태 확인
kroot link status

연결 정보는 프로젝트 안의 .kroot/project.json에 저장됩니다. 이후 hooks와 stage CLI는 이 파일을 기준으로 세션, 대화, 산출물, 단계별 카드 데이터를 kroot-server에 동기화합니다.

4. kroot-proto 연동 방식 ​

kroot-proto는 실행 서버가 아니라 API 계약 저장소입니다. kroot-adk와 kroot-server는 모두 다음 import 경로를 사용합니다.

go
import "github.com/jikime/kroot-proto/gen/kroot/v1"

로컬 개발에서는 두 저장소 모두 go.mod에서 형제 폴더를 참조합니다.

go
replace github.com/jikime/kroot-proto => ../kroot-proto

proto를 바꿨다면 생성 코드를 먼저 갱신합니다.

bash
cd ../kroot-proto
buf generate
go test ./...

그다음 소비자 저장소에서 빌드가 깨지지 않는지 확인합니다.

bash
cd ../kroot-adk
go test ./...

cd ../kroot-server
go test ./...

실무에서는 proto 변경이 가장 넓은 영향을 주기 때문에, 필드 삭제나 이름 변경처럼 깨질 수 있는 변경은 먼저 buf breaking 또는 PR 리뷰로 확인하는 것이 안전합니다.

5. MCP Gateway 연동 ​

KRoot 스택에서 현재 실제 MCP Connector 역할을 하는 것은 kroot-server 안의 kroot-mcp-gateway입니다. 이 바이너리는 kroot-server와 같은 DB, S3, JWT secret을 사용하지만, gRPC 서버와는 별도로 실행됩니다.

로컬 Claude Code에서만 확인할 때는 HTTP로 실행해도 됩니다.

bash
cd ../kroot-server
set -a
source secrets.env
set +a

go run ./cmd/kroot-mcp-gateway --http :8600 --issuer-url http://localhost:8600

상태 확인은 다음처럼 합니다.

bash
curl http://localhost:8600/healthz
curl http://localhost:8600/.well-known/oauth-authorization-server

kroot-adk/templates/.mcp.json에는 이미 kroot MCP 서버 설정 예시가 들어 있습니다.

json
{
  "mcpServers": {
    "kroot": {
      "type": "http",
      "url": "${KROOT_MCP_URL:-http://localhost:8600/mcp}",
      "headers": {
        "Authorization": "Bearer ${KROOT_JWT}"
      }
    }
  }
}

Claude Code를 실행하기 전에 CLI JWT를 환경 변수로 넘깁니다.

bash
export KROOT_MCP_URL=http://localhost:8600/mcp
export KROOT_JWT="$(kroot auth token)"
claude

로컬 Claude Code는 OAuth를 다시 하지 않고 kroot auth login으로 받은 CLI JWT를 재사용합니다. 반대로 Claude.ai Custom Connector나 Claude Desktop 원격 Connector로 붙일 때는 공개 HTTPS URL이 필요합니다.

운영 배포 흐름은 다음과 같습니다.

bash
# kroot-server 저장소 기준
docker build -f deploy/docker/Dockerfile.mcp-gateway -t kroot-mcp-gateway .
docker run -d --name kroot-mcp-gateway --restart=always \
  --env-file /etc/kroot/secrets.env \
  -p 127.0.0.1:8600:8600 \
  kroot-mcp-gateway

운영 환경에서는 KROOT_MCP_ISSUER_URL을 실제 공개 HTTPS 주소로 설정해야 합니다.

dotenv
KROOT_MCP_HTTP_ADDR=:8600
KROOT_MCP_ISSUER_URL=https://mcp.example.com
KROOT_MCP_ACCESS_TTL=1h
KROOT_MCP_AUTH_CODE_TTL=60s
KROOT_MCP_SESSION_IDLE=10m
KROOT_MCP_LOCAL_PROJECT_ROOT=/srv/kroot/workspaces

Caddy를 쓰면 /mcp, /oauth/*, /.well-known/*, /healthz를 localhost:8600으로 프록시하고 TLS 인증서를 자동으로 발급받을 수 있습니다. Claude.ai는 localhost나 사설 IP에 연결할 수 없으므로, Custom Connector에는 반드시 https://<도메인>/mcp 형태의 공개 주소를 등록해야 합니다.

6. kroot-mcp-server 패키지와의 차이 ​

kroot-ui-refctoring/packages/kroot-mcp-server에는 @kroot/kroot-mcp-server 패키지가 있습니다. 이 패키지는 현재 README 기준으로 WS Job을 받아 로컬 kroot-dev CLI를 호출하기 위한 스캐폴드입니다.

간단히 구분하면 다음과 같습니다.

이름위치현재 용도
kroot-mcp-gatewaykroot-server/cmd/kroot-mcp-gatewayClaude.ai/Claude Code가 호출하는 실제 MCP HTTP Gateway
@kroot/kroot-mcp-serverkroot-ui-refctoring/packages/kroot-mcp-serverWS Job -> 로컬 CLI 브리지 스캐폴드, npm 패키지 형태

따라서 KRoot 프로젝트, 워크플로우, S0~S12 단계 도구를 Claude Connector에 노출하려면 kroot-mcp-gateway를 기준으로 보면 됩니다. kroot-adk는 더 이상 별도 STDIO MCP 서버를 제공하지 않습니다. @kroot/kroot-mcp-server는 별도 WS 기반 실행 에이전트 흐름을 구현할 때 참고하거나 후속 개발 대상으로 다루는 편이 좋습니다.

7. Agent와 MCP 계약 확인 ​

ADK의 stage agent 템플릿과 서버 MCP prompt가 같은 산출물 계약을 따르는지 확인하려면 다음 스크립트를 사용합니다.

bash
cd ../kroot-adk
python3 scripts/check_stage_contracts.py --server-root ../kroot-server

이 검사는 Claude Code 템플릿과 MCP prompt가 서로 다른 산출물 형식을 요구하는 실수를 줄여 줍니다.

자주 보는 문제 ​

증상확인할 것
kroot: command not found~/.local/bin 또는 설치 경로가 PATH에 들어 있는지 확인합니다.
KROOT_DB_URL is requiredkroot-server 실행 전에 set -a; source secrets.env; set +a를 실행했는지 확인합니다.
/readyz 실패PostgreSQL 실행 여부, Prisma migration 적용 여부, KROOT_DB_URL 값을 확인합니다.
invalid email or password웹 UI 또는 seed로 사용자가 먼저 생성되어 있는지 확인합니다.
invalid_token 또는 unauthenticatedkroot auth login을 다시 실행하고, 서버와 MCP Gateway의 KROOT_JWT_SECRET이 같은지 확인합니다.
MCP가 401 응답export KROOT_JWT="$(kroot auth token)"을 다시 실행합니다.
Claude.ai Connector가 연결 실패공개 DNS, HTTPS, 방화벽 80/443, KROOT_MCP_ISSUER_URL을 확인합니다.
proto import 오류../kroot-proto 위치와 각 저장소의 go.mod replace 경로를 확인합니다.
