kroot 브라우저 기반 PAT 로그인 — 설계 문서 ​

  • 날짜: 2026-06-23
  • 상태: 설계 확정 대기(사용자 리뷰 후 구현 계획으로)
  • 범위: kroot-adk(CLI, Go) + kroot/backend/server/auth(Spring Authorization Server). kroot-server(Go/gRPC)는 변경 없음.

1. 목표 ​

kroot init / kroot auth login의 인증을 이메일+비밀번호 대화형에서 브라우저 기반 로그인(Claude Code / Codex 구독 로그인 방식)으로 전환한다. 데스크톱은 loopback 리디렉션, 헤드리스/SSH는 device 코드 플로우로 지원한다. 발급되는 자격증명은 기존 PAT(kpat_) 를 재사용한다.

확정된 결정 ​

#결정값
Q1실행 환경loopback + device 폴백 둘 다
Q2이메일+비번완전 제거. 자동화/CI는 --token / KROOT_TOKEN
Q3토큰 모델기존 PAT(kpat_) 재사용 (kroot-server 검증 변경 0)
D1PAT 만료90일 + CLI 자동 재발급(silent re-auth). 서버 만료 모델 변경 없음
D2헤드리스Device Authorization Grant(RFC 8628)를 인증 서버에 추가

2. 현재 상태 (코드 확인 결과) ​

이미 존재 — 데스크톱 loopback은 서버 작업 0 ​

인증 서버 kroot/backend/server/auth(포트 17020):

  • OAuth2 Authorization Server: /authorize, /token, formLogin /login 페이지.
  • kroot-cli-app public 클라이언트(application-dev.yml): public-client: true(PKCE), grant-types: [authorization_code], redirect-uris: [http://127.0.0.1:17298/callback], scopes: [openid, profile, email]. 주석에 본 설계 흐름이 그대로 명시됨.
  • POST /api/me/credentials(PatController): 인증된 사용자가 PAT 발급. 요청 {name, scopes, expiresDays}, 응답 {id, token(평문 1회), tokenPrefix, expiresAt}. form 세션 / Bearer JWT / PAT 인증 모두 허용(CurrentUser).
  • PatService.issue(...): DEFAULT_EXPIRES_DAYS=90, MAX_EXPIRES_DAYS=90(초과 시 clamp), PER_USER_QUOTA=5. ALLOWED_SCOPES에 kroot.cli.read, kroot.cli.write 포함.
  • PAT introspection(/api/internal/pat/introspect): kroot-server가 이미 호출(M2M client kroot-server).

없음 — 추가 필요 ​

  • Device Authorization Grant: kroot-cli-app은 loopback authorization_code 전용. device 엔드포인트·검증 페이지 없음. (D2)

CLI 현재 상태 (kroot-adk) ​

  • cmd/authcmd/login.go: 이메일+비번 또는 --token kpat_…(저장 후 종료). OS 키체인 저장 존재.
  • cmd/initcmd/backend.go: loginInteractive(이메일+비번 대화형).
  • cmd/authcmd/{logout,token,whoami}.go, status.go 존재.

3. 아키텍처 / 인증 흐름 ​

3.1 Loopback (데스크톱 기본) ​

kroot init | kroot auth login
 1. CLI: 127.0.0.1:17298 콜백 서버 기동 (포트 사용 중이면 D2 폴백 또는 대체 포트는 §7)
 2. CLI: PKCE code_verifier/code_challenge + state(난수) 생성
 3. CLI: 브라우저 오픈 → GET {issuer}/authorize
        ?response_type=code&client_id=kroot-cli-app
        &redirect_uri=http://127.0.0.1:17298/callback
        &scope=openid profile email&state=<state>
        &code_challenge=<chal>&code_challenge_method=S256
 4. 사용자: 기존 /login 폼으로 로그인 (+ 최초 동의)
 5. 서버: 302 → http://127.0.0.1:17298/callback?code=<code>&state=<state>
 6. CLI: state 검증 → POST {issuer}/token (code + code_verifier) → access_token(JWT, 단기)
 7. CLI: POST {issuer}/api/me/credentials  (Authorization: Bearer <access_token>)
        body {name:"cli@<hostname>", scopes:["kroot.cli.read","kroot.cli.write"], expiresDays:90}
        → {token:"kpat_…", expiresAt}
 8. CLI: kpat_ 를 OS 키체인에 저장 (기존 --token 저장 경로 재사용) + expiresAt 메타 기록
 9. 브라우저에 "로그인 완료, 터미널로 돌아가세요" 페이지 표시

access_token 은 PAT 발급에만 쓰고 버린다(저장하지 않음). 장수명 자격은 PAT.

3.2 Device 코드 (헤드리스/SSH) — D2 ​

서버에 Device Authorization Grant 추가 후:

kroot auth login --device  (또는 브라우저 오픈 실패 시 자동 폴백)
 1. CLI: POST {issuer}/oauth2/device_authorization (client_id=kroot-cli-app, scope=...)
        → {device_code, user_code, verification_uri, verification_uri_complete, interval, expires_in}
 2. CLI: 터미널 표시 "브라우저에서 {verification_uri} 열고 코드 {user_code} 입력"
        (가능하면 QR/verification_uri_complete 도)
 3. 사용자: 다른 기기 브라우저에서 로그인 + user_code 승인(동의)
 4. CLI: POST {issuer}/token (grant_type=device_code, device_code) 를 interval 간격 폴링
        → authorization_pending / slow_down / access_denied / expired_token 표준 처리
        → 승인되면 access_token
 5. 이후 §3.1 의 7~8 과 동일(/api/me/credentials → kpat_ → 키체인)

3.3 자동 재발급 (silent re-auth) — D1 ​

  • CLI는 저장 시 PAT 의 expiresAt 를 함께 보관.
  • 명령 실행 전 또는 gRPC가 PAT 만료로 Unauthenticated 반환 시:
    • 만료 임박(예: < 3일) 또는 만료됨 → §3.1/§3.2 플로우를 자동 1회 재실행해 새 PAT 발급·교체.
    • 비대화형(CI, KROOT_TOKEN/--token) 환경에서는 자동 재인증을 시도하지 않고 명확한 에러 + 안내.
  • 결과적으로 사용자 체감은 "만료 없음"이되 서버의 90일 만료/회전 보안은 유지.

4. 컴포넌트별 변경 ​

4.1 CLI (kroot-adk, Go) ​

  • 신규 internal/auth/browserlogin/(또는 유사):
    • loopback.go — 콜백 HTTP 서버, 포트 17298(점유 시 §7), 완료 페이지.
    • pkce.go — code_verifier/challenge(S256), state 난수.
    • browser.go — open/xdg-open/rundll32 브라우저 오픈(실패 감지 → device 폴백).
    • device.go — device_authorization 요청 + 폴링(interval/slow_down 준수).
    • flow.go — access_token 획득 → /api/me/credentials 호출 → PAT 반환(loopback/device 공통).
  • 수정 cmd/authcmd/login.go: 이메일+비번 제거. 기본 = 브라우저 플로우. --device 강제 device. --token/KROOT_TOKEN 유지(CI). 성공 시 키체인 저장.
  • 수정 cmd/initcmd/backend.go: loginInteractive(이메일+비번) → 브라우저 플로우 호출. promptPassword·이메일 프롬프트 제거.
  • 수정 토큰 저장소: PAT + expiresAt 메타 저장(자동 재발급 판단용). 기존 키체인 추상화 확장.
  • 수정 cmd/authcmd/logout.go: 키체인 PAT 삭제 + 가능하면 DELETE /api/me/credentials/{id}로 서버 revoke.
  • 설정: issuer 는 서버 discovery(auth_discovery)에서 가져옴 — CLI에 하드코딩하지 않음. client_id kroot-cli-app, redirect 포트 17298 는 상수/설정.

4.2 인증 서버 (kroot/backend/server/auth, Spring) — D2만 ​

  • Device Authorization Grant 활성화(Spring Authorization Server OAuth2AuthorizationServerConfigurer device 지원):
    • kroot-cli-app(또는 전용 device 클라이언트)에 urn:ietf:params:oauth:grant-type:device_code grant 추가.
    • /oauth2/device_authorization 엔드포인트 노출.
    • device 검증 UI 페이지(user_code 입력/승인) — 기존 /login 세션 재사용.
    • 보안 체인(DefaultSecurityConfig)에 device 엔드포인트·검증 페이지 경로 허용.
  • PAT 발급/검증/만료 모델은 변경 없음(D1=b 채택으로 무기한 PAT 불필요).

4.3 kroot-server (Go/gRPC) ​

  • 변경 없음. CompositeVerifier + SpringPATVerifier introspection 이 이미 kpat_ 수용.

5. 데이터 / 토큰 / 정책 ​

  • PAT name: cli@<hostname> (기기 식별). 동일 기기 재로그인 시 기존 동일-name PAT 를 revoke 후 재발급(quota 보호).
  • scopes: kroot.cli.read, kroot.cli.write.
  • PER_USER_QUOTA=5: 재로그인이 quota 초과를 유발하지 않도록 자기 기기 PAT 정리. 초과 시 사용자에게 목록·revoke 안내.
  • 키체인 저장 키: 기존 스킴 유지(이슈어/사용자별).

6. 보안 고려 ​

  • PAT 평문은 발급 응답 1회만, 키체인에만 저장(로그/파일 평문 금지).
  • loopback: state + PKCE(S256)로 코드 인터셉트/CSRF 방지. redirect_uri 정확 매칭(127.0.0.1:17298).
  • device: interval 준수, slow_down 백오프, expires_in 후 만료. user_code 충분한 엔트로피(서버 기본).
  • access_token 은 저장하지 않음(PAT 발급에만 사용).
  • logout 은 서버 revoke 까지 시도해 분실 기기 차단.
  • 자동 재발급은 대화형에서만(비대화형은 명시적 실패).

7. 에러 / 엣지 ​

  • 포트 17298 점유: 등록된 redirect_uri 가 고정이라 임의 포트는 불가 → (1) 짧게 대기 후 재시도, (2) 그래도 안 되면 device 폴백 안내. (대체 포트를 쓰려면 서버 redirect_uri 추가 등록 필요 — §13.)
  • 브라우저 오픈 실패(헤드리스) → device 폴백 자동.
  • state 불일치 / code 만료 → 거부 + 재시도.
  • device: authorization_pending(계속 폴링), slow_down(interval 증가), access_denied(중단), expired_token(재시작 안내).
  • quota 초과(5개) → 활성 PAT 목록 표시 + revoke 안내.
  • 네트워크/서버 다운 → 명확한 메시지, 키체인 기존 토큰 보존.

8. 테스트 전략 ​

  • CLI 단위: PKCE 생성, state 검증, 콜백 파싱, device 폴링 상태머신(pending/slow_down/denied/expired), 자동 재발급 트리거(만료 임박/401), 비대화형 비-재인증.
  • CLI 통합: 모의 인증 서버(/authorize,/token,/api/me/credentials,/oauth2/device_authorization)로 loopback·device E2E.
  • 서버: device grant 발급·승인·폴링·만료 통합 테스트(기존 OAuth2TestClient 패턴 확장).
  • 회귀: --token/KROOT_TOKEN CI 경로 유지 확인. 이메일+비번 제거로 깨지는 호출부 정리.

9. 범위 밖 / 후속 ​

  • 무기한 PAT(서버 만료 모델 변경) — D1=b 로 제외.
  • refresh_token 회전 기반 모델(Q3-2) — 제외.
  • 대체 loopback 포트 동적 등록.

10. 미해결 질문(구현 전 확인) ​

  1. redirect 포트 17298 고정 유지 가정(점유 시 device 폴백). 동적 포트가 필요하면 서버 redirect_uri 정책 변경 필요.
  2. device 검증 UI 의 디자인/문구(기존 /login 테마 재사용 가정).
  3. kroot logout 서버 revoke 의 PAT id 확보 방법(발급 시 id 저장 가정).
