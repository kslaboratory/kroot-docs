CLI Invocation Model ​

The SDK spawns the CLI as a subprocess with these flags:

claude --output-format stream-json --verbose --input-format stream-json [--permission-mode <mode>]

--input-format stream-json and --output-format stream-json put the CLI in headless bidirectional mode:

  • stdout — newline-delimited JSON; one message per line (framing: \n)
  • stdin — newline-delimited JSON; one message per line (same framing)

--print (-p) is not passed explicitly; stdin-as-pipe implies non-interactive mode automatically.

§1 — User Input Message Schema (stdin → CLI) ​

Initial prompt ​

Source: SDKUserMessage type (SDK A) + live capture (B).

json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": "Your prompt text here"
  },
  "parent_tool_use_id": null
}

Required fields: type, message.role, message.content, parent_tool_use_id
Optional fields: uuid (UUIDv4 string), session_id (UUIDv4), timestamp (ISO 8601), isSynthetic, shouldQuery, priority ("now"|"next"|"later"), subagent_type, task_description

Multi-turn (subsequent messages, same session) ​

Same structure. The CLI tracks session state internally; you do not resend previous messages. Optionally include session_id matching the one from the system/init message to be explicit:

json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": "Follow-up question"
  },
  "parent_tool_use_id": null,
  "session_id": "83d386df-feb8-457b-98ce-178af96aede0"
}

Resuming a previous session ​

Pass --resume <session_id> or --session-id <session_id> as CLI flags at startup. Once running, the same user message format is used. The session_id can be obtained from the session_id field of any prior result message.

§2 — can_use_tool control_request Schema (CLI stdout → consumer) ​

Source: SDKControlPermissionRequest type (SDK A). NOT captured live — see §6 Gotcha #1.

When Claude wants to execute a tool that requires a permission decision, the CLI emits this on stdout:

json
{
  "type": "control_request",
  "request_id": "f3a9b2c1d0e",
  "request": {
    "subtype": "can_use_tool",
    "tool_name": "Write",
    "input": {
      "file_path": "/tmp/outside-cwd.txt",
      "content": "hello"
    },
    "tool_use_id": "toolu_01GoBkpoeJQKnctBgrvai2r9",
    "permission_suggestions": [],
    "blocked_path": "/tmp/outside-cwd.txt",
    "decision_reason": "Writing outside the allowed working directory",
    "decision_reason_type": "workingDir",
    "title": "Write file",
    "display_name": "Write",
    "description": "Claude wants to write to /tmp/outside-cwd.txt",
    "agent_id": null
  }
}

Key fields:

FieldTypeRequiredNotes
type"control_request"yesAlways this literal
request_idstringyesCorrelate with your control_response
request.subtype"can_use_tool"yesAlways this literal for permission requests
request.tool_namestringyese.g. "Write", "Bash", "Edit"
request.inputobjectyesThe tool's arguments
request.tool_use_idstringyesThe tool_use block ID from the preceding assistant message
request.permission_suggestionsarrayoptionalSuggested PermissionUpdate rules to add if user approves permanently
request.blocked_pathstringoptionalPath that triggered the request
request.decision_reasonstringoptionalHuman-readable reason
request.decision_reason_typestringoptional`"rule"
request.classifier_approvablebooloptionalWhether a safety check may be classifier-approved
request.titlestringoptionalPermission display title
request.display_namestringoptionalShort tool label
request.descriptionstringoptionalSubtitle/description
request.agent_idstringoptionalPresent when tool call is from a subagent

§3 — control_response Schema (consumer stdin → CLI) ​

Source: ControlResponse/ControlErrorResponse types + SDK .mjs handleControlRequest code (SDK A).

The consumer must write a response to stdin before the CLI can continue. Each response must echo the request_id from the matching control_request. One response per request.

Allow ​

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "f3a9b2c1d0e",
    "response": {
      "behavior": "allow",
      "toolUseID": "toolu_01GoBkpoeJQKnctBgrvai2r9"
    }
  }
}

Allow with modified input (updatedInput) ​

Use when you want to modify tool arguments before execution (e.g., redirect a file path):

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "f3a9b2c1d0e",
    "response": {
      "behavior": "allow",
      "updatedInput": {
        "file_path": "/approved/path/file.txt",
        "content": "hello"
      },
      "toolUseID": "toolu_01GoBkpoeJQKnctBgrvai2r9"
    }
  }
}

Deny ​

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "f3a9b2c1d0e",
    "response": {
      "behavior": "deny",
      "message": "Permission denied by host",
      "interrupt": false,
      "toolUseID": "toolu_01GoBkpoeJQKnctBgrvai2r9"
    }
  }
}
  • message (string) — returned to Claude as the tool_result error
  • interrupt (bool, optional, default false) — when true, Claude's current turn is aborted after the denial

Error response (e.g., no handler available) ​

json
{
  "type": "control_response",
  "response": {
    "subtype": "error",
    "request_id": "f3a9b2c1d0e",
    "error": "canUseTool callback not provided",
    "pending_permission_requests": []
  }
}

pending_permission_requests carries any control_requests that were queued while waiting for this error response to be sent.

Allow with permanent permission rules (updatedPermissions) ​

Optional: instruct the CLI to persist a permission rule so the user is not asked again:

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "f3a9b2c1d0e",
    "response": {
      "behavior": "allow",
      "updatedPermissions": [
        {
          "type": "addRules",
          "rules": [{ "toolName": "Write", "ruleContent": "/tmp/**" }],
          "behavior": "allow",
          "destination": "session"
        }
      ],
      "toolUseID": "toolu_01GoBkpoeJQKnctBgrvai2r9"
    }
  }
}

§4 — Interrupt / Abort Control Message (consumer stdin → CLI) ​

Source: SDKControlInterruptRequest type + SDK .mjs (SDK A).

To stop the in-progress conversation turn, write to stdin:

json
{
  "type": "control_request",
  "request_id": "irq_abc123",
  "request": {
    "subtype": "interrupt"
  }
}

The CLI responds on stdout with a control_response:

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "irq_abc123"
  }
}

After this, the turn ends and the CLI emits a result message. There is no separate SIGINT/process-signal abort mechanism in the SDK protocol; the SDK uses stdin EOF + a ~2 s grace window for clean shutdown.

For an immediate (non-graceful) kill: close the subprocess. The SDK normally avoids this to let the CLI run gracefulShutdown.

§5 — session_id Surfacing ​

Source: SDKSystemMessage type (SDK A) + live capture (B).

The session_id (a UUID string) is first available in the system/init message, which is always the first substantive message emitted on stdout after hooks fire:

json
{
  "type": "system",
  "subtype": "init",
  "session_id": "83d386df-feb8-457b-98ce-178af96aede0",
  "cwd": "/path/to/working/dir",
  "permissionMode": "default",
  "model": "claude-opus-4-8[1m]",
  "tools": ["Bash", "Write", "Edit", ...],
  "mcp_servers": [...],
  "slash_commands": [...],
  "apiKeySource": "none",
  "claude_code_version": "2.1.195",
  "output_style": "default",
  "uuid": "cb08c510-a0e8-403c-9fae-3fc87b859e55"
}

The same session_id is echoed in every subsequent message (assistant, user, result, system, rate_limit_event, etc.). The definitive end-of-turn session_id is in the result message:

json
{
  "type": "result",
  "subtype": "success",
  "session_id": "83d386df-feb8-457b-98ce-178af96aede0",
  "result": "Hello, nice to meet!",
  "is_error": false,
  "num_turns": 1,
  "total_cost_usd": 0.186743,
  ...
}

To resume the session later: claude --resume 83d386df-feb8-457b-98ce-178af96aede0 --output-format stream-json --input-format stream-json --verbose

§6 — Gotchas, Ordering, Required Fields ​

Gotcha 1: can_use_tool NOT captured live (USER SETTINGS INTERFERENCE) ​

The implementation plan MUST account for this uncertainty.

User-level ~/.claude/settings.json contains:

json
{
  "skipDangerousModePermissionPrompt": true,
  "skipAutoPermissionPrompt": true
}

These settings caused the CLI to auto-deny permission prompts WITHOUT emitting a control_request on stdout — instead returning the denial directly as a tool_result error ("Claude requested permissions to write to ..., but you haven't granted it yet."). The --settings flag override did not clear these entries from the effective settings.

Recommendation for implementation: Test can_use_tool flow either:

  1. In a clean environment where user settings do not have skipDangerousModePermissionPrompt: true, OR
  2. By running the SDK's Node.js integration test with canUseTool callback configured

The schema in §2–§3 is taken directly from SDKControlPermissionRequest (.d.ts) and confirmed by the SDK's processControlRequest + handleControlRequest source in sdk.mjs. It is NOT observed from live traffic.

Gotcha 2: Bidirectional control_request / control_response ​

The protocol is fully bidirectional — not just CLI→SDK for permission:

DirectionMessage typeWhen used
consumer stdin → CLIcontrol_requestinterrupt, initialize, set_model, set_permission_mode, get_settings, etc.
consumer stdin → CLIcontrol_responseresponding to CLI's can_use_tool permission request
CLI stdout → consumercontrol_requestcan_use_tool (permission), hook_callback
CLI stdout → consumercontrol_responseresponding to consumer's initialize, interrupt, etc.

Both type:"control_request" and type:"control_response" can appear in both directions.

Gotcha 3: initialize handshake ​

The SDK sends an initialize control_request to the CLI before sending any user message. This is optional from the CLI's perspective (the CLI starts and accepts user messages without it), but required to configure hook callbacks and SDK MCP servers:

Consumer → CLI stdin:

json
{
  "type": "control_request",
  "request_id": "init_abc",
  "request": {
    "subtype": "initialize",
    "hooks": {},
    "sdkMcpServers": null,
    "systemPrompt": null,
    "appendSystemPrompt": null,
    "agents": null,
    "title": null
  }
}

CLI → consumer stdout (response):

json
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "init_abc",
    "response": {
      "commands": [...],
      "agents": [...],
      "models": [...],
      "output_style": "default",
      "available_output_styles": [...],
      "account": { "email": "...", "subscriptionType": "..." }
    }
  }
}

Live capture confirmed this handshake works correctly (Gotcha 3 is verified live).

Gotcha 4: Newline framing ​

Every JSON object on stdin or stdout is followed by exactly \n (LF). No BOM, no \r\n. The CLI uses line-delimited JSON (NDJSON). The SDK code: this.transport.write(B$(J) + '\n').

Gotcha 5: request_id correlation ​

  • The control_request.request_id is a short random alphanumeric string generated by the consumer (e.g., Math.random().toString(36).substring(2,15) in the SDK)
  • The control_response.response.request_id must exactly match the control_request.request_id
  • The CLI uses this to route responses to waiting handlers

Gotcha 6: stdin must remain open ​

When a can_use_tool control_request is emitted, the CLI blocks the tool execution until the response arrives. stdin must stay open (do not close the write pipe) while the session is active. Closing stdin is the EOF signal that triggers graceful shutdown.

Gotcha 7: control_cancel_request (from CLI to consumer) ​

If the CLI cancels a pending permission request (e.g., the turn is interrupted), it emits:

json
{
  "type": "control_cancel_request",
  "request_id": "f3a9b2c1d0e"
}

The consumer should drop any pending handler for that request_id.

Gotcha 8: session_id in output messages but optional in input ​

The session_id in SDKUserMessage.session_id is marked optional in the type. The CLI infers the session from the process itself. You do not need to include it in stdin messages; include it only if you want explicit correlation.

Gotcha 9: --input-format stream-json requires --verbose when --output-format stream-json ​

Error: When using --print, --output-format=stream-json requires --verbose

Always pass --verbose alongside --output-format stream-json.

Gotcha 10: toolUseID in control_response ​

The consumer is expected to echo toolUseID (camelCase) in the response.response body of the control_response. The SDK derives this from request.tool_use_id (snake_case) in the incoming control_request. This field allows the CLI to correlate the permission decision with the specific tool call in a multi-tool batch.

Message Sequence Diagram (normal turn) ​

consumer (stdin) →→→  CLI  →→→ consumer (stdout)
                              hook_started (SessionStart)
                              hook_response (SessionStart)
                              system/init  ← session_id first appears here
[optional] initialize ──→     control_response (init data)
user message ─────────→
                              assistant (text/thinking)
                              assistant (tool_use: Write)
                ←─────────── control_request (can_use_tool)
control_response (allow) ──→
                              user (tool_result: success)
                              assistant (final text)
                              rate_limit_event
                              result (subtype:success)  ← session_id + cost

What the Implementation Plan Must Account For ​

  1. can_use_tool is not yet confirmed live — validate in a clean environment or via SDK Node.js test.
  2. stdin must stay open as a writable stream throughout the session lifecycle.
  3. request_id generation — use a UUID or random string; must be unique per session.
  4. toolUseID in allow/deny response — echo request.tool_use_id as toolUseID in the response body.
  5. Bidirectional message routing — the consumer must multiplex two concurrent operations on the same stdin: writing user messages AND writing control_responses to incoming permission requests.
  6. Error response with pending_permission_requests — if a consumer sends an error response to a non-permission control_request, the CLI may include queued can_use_tool requests in the error; process them.
  7. control_cancel_request — handle cancellation of pending permission requests.
  8. interrupt response — CLI responds with control_response { subtype:"success" } on stdout; after interrupt, a result message follows.
