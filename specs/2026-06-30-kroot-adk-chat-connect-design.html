KROOT-ADK-CHAT-CONNECT 설계 ​

작성: 2026-06-30 · 갱신: 2026-06-30 (옵션 A 확정 반영) · 상태: 설계(Draft) 범위: 원격 웹 ↔ 사용자 노트북 로컬 Claude Code CLI 연결 선행 문서: AICODING-CHAT-WS-CLI-ARCHITECTURE.md (kroot 컨테이너 레포 docs/) ⚠️ 본 문서의 frontend/…·server.ts·src/… 경로는 kroot 컨테이너 레포(kroot-main-site) 기준이며 kroot-adk 레포가 아니다(레퍼런스용). kroot-adk 경로는 cmd/…·internal/….

원격 서버에 호스팅된 kroot 웹사이트의 aicoding 채팅에서 메시지를 보내면, 사용자 노트북에 설치된 kroot-adk(Go) 데몬이 그 노트북의 claude(Claude Code CLI)를 직접 구동해 응답을 돌려준다. 노트북은 NAT/방화벽 뒤(인바운드 불가)에 있다고 가정하고, 서버를 아웃바운드 릴레이로 사용한다.

결정 요약 (이 문서의 전제) ​

  • 토폴로지: 아웃바운드 릴레이(변형 B). 브라우저↔서버=WebSocket, 데몬↔서버=gRPC 양방향 스트림, 릴레이=WS↔gRPC 브리지.
  • 데몬 구현: 옵션 A — 순수 Go. kroot-adk(Go)가 claude CLI를 stream-json으로 직접 구동한다. Node/@anthropic-ai/claude-agent-sdk를 쓰지 않는다(노트북에 Node 런타임 무의존, 단일 Go 바이너리 유지).
  • 인증: kroot-adk의 기존 PAT(kpat_) 를 재사용. 데몬→서버 gRPC metadata 의 Bearer 로 제시, 서버에서 검증.
  • 폴백: 프로토콜 유지보수 부담이 크면 §11.1 의 옵션 D(얇은 Node 실행기)로 시작했다가 A로 수렴.

1. 목표 / 비목표 ​

목표 ​

  • 웹은 원격 전용(로컬 호스팅 안 함). 사용자는 일반 브라우저로 원격 사이트를 본다.
  • 채팅 입력 → 사용자 노트북의 claude CLI 가 노트북의 파일/프로젝트 를 대상으로 실행.
  • 인증은 PAT(kpat_) 로 통일(kroot-adk·웹·서버 동일 토큰 체계).
  • 노트북에 인바운드 포트를 열지 않는다. NAT/방화벽/회사망 뒤에서도 동작.
  • kroot-adk 의 단일 Go 바이너리 배포를 깨지 않는다(Node 런타임 무의존).

비목표 ​

  • 서버 인프라에서 CLI를 실행하는 공유 실행 모델(파일 대상이 노트북이 아니게 됨).
  • 기존 로컬 dev / Tauri 경로 폐기(병행 가능).
  • claude/Claude Agent 자체의 재구현 — 에이전트 엔진은 claude 바이너리가 담당하고, kroot-adk 는 그 CLI를 모는 클라이언트만 만든다.

2. 배경 / 현재 상태 ​

  • 현 aicoding 채팅은 server.ts(Node, Agent 사이드카 startAgentSidecar)가 /ws/chat을 서빙하고 @anthropic-ai/claude-agent-sdk query() 로 로컬 claude CLI를 spawn한다. 이 경로(server.ts + CLI)는 원격 dev/prod 배포에 없다(프로덕션=standalone Next + socket + mcp-hub). 상세: docs/AICODING-CHAT-WS-CLI-ARCHITECTURE.md.
  • kroot-adk 는 별도 Go 레포(github.com/kslaboratory/kroot-adk, cobra, 단일 바이너리)이며 이미 다음을 보유 → 재사용:
    • PAT 인증: internal/auth/browserlogin(PKCE 브라우저 로그인 → 장수명 kpat_… 발급·저장, access token 미저장, --token/KROOT_TOKEN 비대화형). 명령: cmd/authcmd(login/token/whoami/status).
    • 서버 연결: internal/serverurl(gRPC 베이스 URL, 예 grpc://localhost:17026), gRPC 스택(grpc/protobuf/kroot-proto).
    • 프로젝트 연결: cmd/linkcmd(link/unlink/status) — 프로젝트↔로컬경로 매핑 토대.
  • 따라서 본 작업은 server.ts(Node) 이식이 아니라 kroot-adk(Go)에 채팅 데몬을 신규 구현하는 것이다. server.ts 는 프로토콜 레퍼런스로만 본다.

4. 토폴로지 — 아웃바운드 릴레이 + WS↔gRPC 브리지 ​

[브라우저(원격 https, 세션쿠키)] ──WebSocket(wss)──► [서버 릴레이] ◄──gRPC bidi stream(outbound, PAT)── [kroot-adk 데몬(노트북)]
                                                          │ user U 매칭                                      └─► claude CLI (stream-json, 노트북 파일 대상)
  • 브라우저 ↔ 서버: WebSocket(브라우저는 WS). 세션 쿠키 인증.
  • 데몬 ↔ 서버: gRPC 양방향 스트림(kroot-adk gRPC 네이티브, proto 재사용). PAT(metadata Bearer) 인증, outbound only.
  • 릴레이: WS 프레임 ↔ gRPC 스트림 메시지를 프로토콜 브리지. 양쪽 페이로드는 동일 chat 메시지(§8).

변형 A(브라우저→localhost) 대비 ​

보안(노트북 인바운드 0)·견고함(localhost/Chrome PNA/mixed-content 회피)·인증 정합(PAT 서버검증) 때문에 릴레이(B)로 확정. A는 폐기 또는 동일 LAN 전용 옵션으로만 잔존(§14 오픈).

5. 아키텍처 / 컴포넌트 ​

  1. 서버 릴레이(신규, Node 측) — 두 입구 + 레지스트리 + 브리지.
    • gRPC 서비스(데몬용): bidi stream AgentConnect. PAT 인터셉터로 user U + agentId 등록.
    • WS 엔드포인트(브라우저용): /ws/chat. 세션 쿠키 → user U. U의 agent와 바인딩.
    • 호스팅: 기존 socket 서비스(ws-runtime.ts, dev 17155 / prod 17255) 합류 vs 전용 서비스(§13, 전용 권장).
  2. kroot-adk 데몬(신규, Go) — 아래 §12 모듈. 기존 auth/serverurl/link 재사용.
  3. kroot-adk stream-json 클라이언트(신규, Go) — claude CLI 드라이버(§9).
  4. 프론트엔드(소규모) — 챗 WS 타깃을 wss://서버/ws/chat(serverStore RemoteServer.secure=true), agent 선택 UI, projectId 전송, no-agent 안내.

릴레이는 dumb pipe: Claude 내용을 해석/저장하지 않고 프레임만 브리지.

6. 연결 수립 시퀀스 ​

① kroot chat connect (노트북, Go)
   - 저장된 PAT 로드(kroot auth login 사전 수행) + serverurl 해석
   - 서버로 gRPC bidi stream 'AgentConnect' open, metadata: authorization: Bearer kpat_...
   - 서버: PAT 검증(인터셉터) → user U, scope aicoding.connect 확인
   - 데몬 → 서버: Register { agentId, hostname, projects:[{id,path,name}] }   (projects 는 link 기반)
   - 서버: 레지스트리[U] 에 agent 스트림 등록

② 브라우저: wss://서버/ws/chat (httpOnly 세션쿠키)
   - 서버: 쿠키 → user U 식별 → AgentsList(U) 송신
   - 브라우저 → 서버: Bind { agentId, channelId }   (1개면 자동)
   - 서버: browserChannel ↔ agentStream 바인딩

③ 정상 연결 — 이후 메시지 브리지(§8)

7. 인증 ​

7.1 데몬 ↔ 서버 (PAT, gRPC) ​

  • kroot-adk 가 보관한 PAT 를 gRPC metadata authorization: Bearer kpat_... 로 제시.
  • 서버 gRPC 인터셉터가 검증(REST 의 PatAuthenticationFilter 와 동등 로직: auth.personal_access_tokens cross-schema read). 별도 인증 신설 없음.
  • 전용 스코프 aicoding.connect 신설 — server::auth PatService.ALLOWED_SCOPES 에 등록. 이 연결 PAT는 최소권한(풀권한 금지). 데몬이 노트북에서 명령/파일 실행을 유발하므로 폭발반경 제한이 핵심.

7.2 브라우저 ↔ 서버 (세션 쿠키, WS) ​

  • 브라우저는 토큰을 들고 있지 않다(BFF). /ws/chat 업그레이드는 httpOnly 세션 쿠키(same-origin wss)로 인증 → user U.

7.3 매칭 규칙 (보안 핵심) ​

  • 릴레이는 browserChannel.user == agentStream.user 일 때만 브리지. 교차 사용자 연결 금지.

8. 프레임 프로토콜 (2계층) ​

8.1 릴레이 계층 (브라우저 WS ↔ 데몬 gRPC) ​

기존 /ws/chat chat 페이로드(type:'chat'|'text'|'thinking'|'permission_request'|'permission_response'|'abort'|'session_id'|'done'|'error')를 그대로 재사용하되, 멀티플렉싱 봉투를 둔다. gRPC 측은 동일 의미의 proto 메시지로 표현.

jsonc
// 제어
{ "type":"register", "agentId":"uuid", "hostname":"macbook", "projects":[{"id":"p1","path":"/Users/me/work/app","name":"app"}] } // 데몬→서버
{ "type":"agents:list", "agents":[ ... ] }                                   // 서버→브라우저
{ "type":"bind", "agentId":"uuid", "channelId":"c-123" }                      // 브라우저→서버
{ "type":"agent:unavailable", "reason":"no-agent-connected" }                 // 서버→브라우저
{ "type":"ping" } / { "type":"pong" }

// 데이터(봉투 + chat 페이로드)
{ "channelId":"c-123", "payload":{ "type":"chat", "sessionId":null, "projectId":"p1", "prompt":"...", "model":"...", "permissionMode":"...", "extendedThinking":false } } // →데몬
{ "channelId":"c-123", "payload":{ "type":"text", "text":"..." } }            // →브라우저
  • 변경점: 기존엔 projectPath(절대경로)를 보냈으나, 릴레이에선 projectId 만 보내고 데몬이 link 목록에서 실제 path 로 해석(임의 cwd 주입 방지, §10).
  • v1 은 channelId 1개(1:1), 멀티탭 mux 는 Phase 2.

8.2 데몬 ↔ claude CLI 계층 (stream-json) — §9 ​

데몬은 8.1 의 chat 페이로드를 claude CLI 의 stream-json 입출력으로 변환한다(아래).

9. claude CLI 프로토콜 클라이언트 (옵션 A 핵심 신규) ​

claude-agent-sdk 는 AI 엔진이 아니라 claude CLI 드라이버다. 따라서 Go 에서 동일 stream-json 프로토콜 클라이언트를 구현한다(에이전트 지능은 claude 바이너리가 담당).

9.1 spawn (os/exec) ​

claude --input-format stream-json --output-format stream-json --verbose \
       [--model <m>] [--permission-mode <pm>] [--resume <id> | --session-id <uuid>]
  with Cmd.Dir = <projectId→path>,  stdin/stdout 파이프

레퍼런스: 같은 코드베이스 frontend/.../src/app/api/agents/chat/route.ts 는 spawn('claude', ['-p', msg, '--output-format','stream-json','--verbose']) 로 SDK 없이 직접 구동. Go 도 동등.

9.2 매핑 표 (Node SDK 옵션 → Go 구현) ​

9.3 기능 패리티 — 스킬·서브에이전트·훅 (설정 소스) ★ ​

헤드리스(claude -p/stream-json)는 인터랙티브와 같은 엔진이다. 스킬·서브에이전트(Task)·훅(PreToolUse 등)·슬래시커맨드(/kroot:*,/sc:*)·MCP 는 인터랙티브 여부가 아니라 로드된 설정 소스에 좌우된다. 즉 "헤드리스라 죽는다"가 아니라 "설정을 안 로드하면 죽는다" 이며, 이는 SDK·직접 CLI 공통 게이트다.

  • 현재 server.ts 의 증거: SDK 에 settingSources: ['user','project'] 를 명시(주석: "user + project settings 로드 — 슬래시 커맨드(/kroot:, /sc: 등) 인식에 필수"). Claude Agent SDK 는 FS 설정(스킬/훅/CLAUDE.md/커맨드)을 기본 미로드하므로 이 옵션이 패리티의 생명줄이다.
  • Option A(Go 직접 spawn) 보장 사항:
    1. Cmd.Dir = projectId→path → 프로젝트 .claude/ + CLAUDE.md 로드.
    2. user + project 설정 로드 보장(= settingSources:['user','project'] 상당). 바레 claude -p 는 보통 user/project 설정을 기본 로드(평소 CLI 동작)하지만, 사용하는 CLI 버전의 print-mode 기본 동작을 검증·핀한다. 필요 시 명시 플래그/--settings 로 강제.
    3. 권한/훅: --permission-mode + can_use_tool control 핸드셰이크(§9.2) → PreToolUse 등 훅 발화 + 사용자 승인 동작.
    4. MCP(사용 시) 설정 로드.
  • 검증 기준(Phase 1 수용 조건): 동일 프로젝트에서 (a) 슬래시커맨드 인식, (b) 스킬 트리거, (c) 서브에이전트 dispatch, (d) PreToolUse/PostToolUse/Stop 훅 발화 가 SDK 경로(server.ts)와 동등함을 골든 비교로 확인.

요지: 새로 짜는 건 "엔진"이 아니라 CLI를 모는 배관 + 설정 재현이다. 같은 claude 바이너리 + 같은 설정 소스면 SDK 와 동일한 스킬/훅/에이전트가 동작한다.

9.4 유지보수 리스크 (명시) ​

  • stream-json/control 프로토콜은 공개 안정 스펙이 아니며 claude CLI 버전에 따라 변할 수 있다. 공식 TS/Python SDK 는 Anthropic 이 추종 유지하지만 Go 재구현은 자체 유지 필요.
  • 설정 소스 기본 동작(§9.3-2)도 CLI 버전에 따라 변할 수 있다 → 버전 핀 대상에 포함.
  • 완화책: 지원 claude CLI 버전 핀 + stream-json/설정로딩 회귀 테스트(golden 출력·기능 패리티) 를 세트로 둔다(§14 Phase 3, §15).

10. 프로젝트 경로 매핑 ​

  • 데몬이 Register 시 노출 프로젝트 목록({id,path,name})을 올린다(cmd/linkcmd 의 link 결과 재사용). 서버/브라우저는 절대경로를 모르고 projectId 로만 지칭.
  • 챗 실행 시 데몬이 projectId → path 변환해 Cmd.Dir 로 사용. 목록에 없는 경로 거부(cwd 화이트리스트).

11.1 폴백 D 경로 ​

프로토콜 드리프트 유지보수가 과하면, Go(전송·인증·릴레이) + 얇은 Node 실행기(claude SDK 글루만, stdio) 로 시작 → 안정화 후 실행기를 §9 의 순수 Go 클라이언트로 교체. Go 측 인터페이스(stream-json 클라이언트 경계)를 동일하게 두면 교체 비용이 낮다.

14. 단계별 스코프 ​

  • Phase 0 — 스캐폴드: kroot chat connect 골격 + internal/chat 경계(인터페이스) 정의 + proto 초안. 기존 auth/serverurl/link 연결 검증.
  • Phase 1 — MVP(1:1, 순수 Go): §9 stream-json 클라이언트 + gRPC 릴레이 1 agent:1 channel + 서버 릴레이/브리지 + 프론트 포인팅 + no-agent. "웹 챗 → 노트북 claude" end-to-end. 수용 조건: §9.3 기능 패리티(스킬/서브에이전트/훅/슬래시커맨드)가 SDK 경로와 동등 함을 확인.
  • Phase 2 — mux/멀티 agent: channelId mux(다중 탭), 사용자당 다중 노트북 agent 선택, 프로젝트 노출 관리 UI.
  • Phase 3 — 운영화: claude CLI 버전 핀 + stream-json 회귀(golden) 테스트, 감사 로그, 재연결 중 세션 복구, 백프레셔, 메트릭.

15. 오픈 질문 ​

  1. 릴레이 호스팅: 기존 socket 합류 vs 전용(§13) — 권장 전용.
  2. 데몬 수명: foreground(stripe listen 식) vs --daemon/launchd·systemd.
  3. 지원 claude CLI 버전 범위 + stream-json/설정로딩 회귀 테스트 골든 관리 주체(§9.4). print-mode 의 user/project 설정 기본 로드 여부를 버전별로 검증·핀(§9.3-2).
  4. 멀티 디바이스: 한 사용자 다중 노트북 agent 기본 선택 규칙.
  5. 재연결 중 진행 세션 정책(중단 vs 복구).
  6. A(localhost) 옵션 잔존 여부(동일 LAN 전용) — 유지/폐기.
  7. D 폴백을 1차에 쓸지(드리프트 리스크 회피) vs 처음부터 A.
